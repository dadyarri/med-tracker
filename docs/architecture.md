# Архитектурные ограничения и инварианты (v1.1)

Источник продуктовых требований: [specification.md](specification.md) v1.2 и актуальный [roadmap.md](roadmap.md). Этот документ фиксирует инженерные ограничения. При расхождении с пользовательским решением не менять требования молча, а оформить вопрос в PR.

## Состав

- Kotlin, Compose/Material3, Room, DataStore, Koin, Coroutines/Flow, Navigation Compose, AlarmManager/NotificationManager. WorkManager только для неточных вспомогательных заданий.
- Один Gradle-модуль `app`; разделять пакеты по функциональным областям, не вводить избыточную многоуровневую архитектуру.
- `ScheduleEngine` — независимый от Android расчёт задач и сроков; `OccurrenceMatcher` — сопоставление фактов с задачами; `AlarmReconciler` — синхронизация БД и системных будильников; `MedicationService` — назначения и факты приёма; `InventoryService` — движения запасов. Логические компоненты, не обязательно отдельные интерфейсы.

## Инварианты

1. Room — источник истины для действий и запланированных задач. `AlarmManager` — производное системное состояние. Receiver перечитывает базу при доставке: payload из `PendingIntent` не может удостоверять актуальное состояние.
2. У одной плановой задачи может быть 0 или 1 актуальная связь с фактом выполнения. Одна фактическая запись автоматически закрывает не более одной задачи. История доставленных сигналов и пропусков не переписывается при позднем выполнении.
3. Сопоставление выполнения хранится отдельно: идентификатор задачи, тип/ID факта, время связи. Удаление/изменение факта пересчитывает связь и будущие оповещения.
4. В группе на одно время задачи имеют независимые состояния и параметры. Сигнал не дублируется при повторной реконсиляции. Автоповтор и snooze не должны конкурировать.
5. Приём лекарства — фактическое событие с `takenAt`, независимо от `createdAt`. Для интервального режима следующий срок определяется последним по времени действительным `takenAt` данного назначения; без первого факта первого интервального будильника нет.
6. Версии назначения — полные снимки схемы с непересекающимися периодами действия. Новое назначение не меняет историю завершённого курса.
7. Количество лекарства ведётся в непротиворечивой базовой единице конкретного препарата. Десятичная точность гарантируется правилами хранения. Сила/концентрация, введённая свободным текстом, не является основанием конвертировать единицы.
8. `StockTransaction` — append-only журнал. Изменение факта приёма создаёт компенсирующую операцию и новую операцию при необходимости; фактический приём и операции над запасами изменяются в одной транзакции Room. Остаток вычисляется по журналу.
9. Упаковка предлагается последняя выбранная; при её недоступности требуется явный выбор. Автоматическое переключение на другую упаковку запрещено.
10. Для смещения приёма лекарства относительно еды ожидаемое время питания — резервный источник срока при отсутствии факта еды. `MealEvent` не обязателен для регистрации `MedicationIntake`; поздняя регистрация еды не создаёт повторный приём или будильник для выполненной задачи.
11. Фактические моменты хранятся как однозначные instants; календарные правила — отдельно. Ручную смену часового пояса в v1 не отслеживаем специальным механизмом.
12. Ошибка планирования будильника не отменяет уже сохранённое действие. Записывается диагностическое состояние, реконсиляция повторяется при штатных событиях.
13. Обновление APK должно сохранять базу; `fallbackToDestructiveMigration` недопустим. Локальный экспорт/восстановление полной копии через SAF входит в ближайший план: версионирование, проверка консистентности, предварительная валидация, атомарное восстановление, round-trip тесты. Облако, сервер и сеть по-прежнему исключены.
14. Напоминания — opt-in; различать QUIET (одно тихое уведомление), NORMAL (одно со звуком) и ALARM (явно выбранный настойчивый будильник). Не выводить UI-агрессивность автоматически из факта наличия расписания; точность доставки определяется реальной необходимостью. Для QUIET/NORMAL не показывать fullscreen и не повторять автоматически. `Mute` останавливает текущий звук и повтор, `Snooze` — отдельное осознанное действие. История фактов не обязана показывать технические события.

## Нерешённые низкоуровневые детали

- Окна сопоставления до планового времени, разрешение ничьих при нескольких подходящих задачах; реализовать детерминированно и покрыть тестами до этапа интеграции.
- Схема хранения долей единиц (например, scaled integer или decimal-string с конвертером) — определить до введения инвентаря.
- Конкретный Android API/набор разрешений и поведение на Samsung — подтверждать документацией и испытанием, не выдавать эмулятор за устройство.
- Временная модель календарного цикла и изменения версий назначений на границах дат — реализовать тестируемо.

## UX-инварианты ревизии 2026-11-05

- Ручной журнал функционирует при отсутствии любых специальных разрешений; обязательного мастера разрешений нет.
- На чистой установке расписания выключены, запрос разрешения происходит в контексте сознательного включения соответствующего режима.
- Миграция не выключает и не повышает интенсивность уже активных лекарственных уведомлений молча.
- Разделение доставленных событий, плановых задач и фактических действий остаётся в данных, но не навязывается основному интерфейсу.
- Будущая резервная копия охватывает Room и необходимые DataStore-настройки с согласованным восстановлением; никакой сетевой передачи медицинских данных.
