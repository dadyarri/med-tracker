# Alarm spike: проверка на Samsung

Этап 1, без медицинских данных. Целевое устройство: Samsung, Android 16 / One UI 8.5.
**Физическое устройство в облаке отсутствует: все пункты ниже пока НЕ проверены.**

## Установка и APK

GitHub Actions → Android APK → успешный запуск → Artifacts → MedTracker-debug-… .
Распаковать артефакт и установить `app-debug.apk`. Разрешить установку из выбранного
источника. Для обновления без удаления данных нужен тот же сертификат подписи.
Workflow использует временную debug-подпись runner-а: между запусками она может
отличаться. Для теста обновления соберите обе версии на одной машине с сохранённым
`~/.android/debug.keystore`. Не удаляйте приложение ради обхода несовпадения подписи,
если важно сохранить локальное состояние. Стабильная release-подпись пока не настроена.

## Реализация и ограничения

Один тест (строка Room id=1), append-only журнал последних событий, DataStore для
мастера. Нет сервера, сети приложения, аналитики, резервного копирования и меддомена.
AlarmManager.setAlarmClock используется и для тихого, и для звукового теста.
Системный значок следующего будильника может появляться и у тихого теста.
Полноэкранное отображение и запуск foreground mediaPlayback-службы контролирует ОС.
Reboot/update receiver только согласует будущие PendingIntent, не запускает UI/аудио.
Обработка после первого разблокирования пользователя; Direct Boot не заявлен.
Недоставленное при выключенном устройстве событие не записывается как доставленное.
«Доставлен receiver-у» не означает доказанный звук или показ уведомления пользователю.

Автоматические JVM-тесты проверяют сроки, grace window, замену/stale token,
идемпотентное восстановление, отсутствие backlog, snooze/лимит и границы окна.
Они не подтверждают фактическую работу Android API или Samsung.

## Проверка исправления лицензий CI

В workflow закреплены Android command-line tools `13114758` (19.0).
Настройка инструмента не устанавливает пакеты автоматически: отдельный шаг сначала
выполняет `sdkmanager --sdk_root="$ANDROID_HOME" --licenses` с конечным файлом
ответов, затем в тот же каталог устанавливаются требуемые SDK-пакеты. Конструкция
`yes | sdkmanager` не используется, чтобы SIGPIPE не маскировал результат при pipefail.

Эти команды выполнены в новом пустом SDK-каталоге: лицензии приняты, установлены
`platforms;android-36` r2, `build-tools;35.0.0` и `platform-tools` 37.0.1, код выхода 0.
Это проверка команд на чистом SDK, а не подтверждение успешного запуска GitHub Actions:
API журналов на момент проверки возвращает 403.

## Экран будильника, версия 0.2-alarm-screen

Со слов владельца: получение разрешений и звук работают. При срабатывании поверх
блокировки открывался главный экран; после его закрытия снова появлялась блокировка.
Это не подтверждение снятия PIN: приложение показывалось поверх keyguard.

В версии 0.2 полноэкранный PendingIntent направлен в отдельную приватную AlarmActivity
с крупными действиями, собственной задачей и без requestDismissKeyguard. Только она
использует showWhenLocked/turnScreenOn; MainActivity больше не использует эти флаги.
Состояние перечитывается из Room, устаревшее окно закрывается; после mute/snooze/cancel
окно закрывается, а операция отложения завершается независимо от lifecycle окна.
Для Android 16 добавлен creator opt-in запуска этого PendingIntent из фона.
Звуковой канал v2 имеет высокую важность и вибрацию для heads-up, аудио по-прежнему
принадлежит службе. Новый ID необходим из-за неизменяемых настроек старого канала.
Тихие сигналы и отключённый звук не открывают AlarmActivity.

`./gradlew assembleDebug testDebugUnitTest lintDebug` — успешно: 26 тестов без
ошибок/пропусков, Lint 0 ошибок / 4 предупреждения. Семь новых Robolectric-проверок
покрывают маршрут и параметры PendingIntent, отказ full-screen, тихий режим, канал,
сохранение keyguard, закрытие старого окна и завершение snooze после закрытия Activity.
Это не физическая проверка показа One UI.

Повторная ручная проверка именно версии 0.2:
- [ ] При блокировке с PIN появляется экран «Тестовый будильник», не мастер настроек.
- [ ] После mute/snooze/cancel возвращается keyguard; другие приложения требуют PIN.
- [ ] При разблокированном телефоне появляется heads-up с действиями. Android может
  предпочесть его полноэкранному окну. Проверить разрешение всплывания канала One UI.
- [ ] При запрете full-screen остаётся уведомление; тап открывает экран будильника.
- [ ] Тихий сигнал не включает экран, не вибрирует и не открывает окно.

## Обновление между сборками CI: постоянная подпись

Владелец сообщил об ошибке «Приложение не установлено» при обновлении APK из двух
разных запусков GitHub Actions. В прежнем workflow каждый временный runner создавал
новый debug.keystore. Такие APK имеют несовместимые сертификаты. Фактические два
APK владельца не извлекались и их сертификаты здесь не сравнивались. У двух APK,
выданных из облачного workspace, сертификаты совпадают, подписи валидны, versionCode 2/3.

Workflow теперь требует репозиторный secret `ANDROID_DEBUG_KEYSTORE_BASE64`,
восстанавливает один стандартный debug-keystore и отказывается генерировать новый
ключ при отсутствии секрета. `scripts/configure-ci-signing.sh` на машине владельца
однократно генерирует/использует ключ вне checkout, сохраняет его через `gh secret set`
и не заменяет уже настроенный секрет. Приватный ключ не выводится и не коммитится.
В артефакт добавлен публичный `signing-certificate.txt` для сравнения SHA-256.

Проверено: `bash -n`, `git diff --check`, два изолированных восстановления одного
временного тестового ключа и подпись APK через apksigner; оба APK проходят verify,
их SHA-256 сертификаты одинаковы. Временные тестовые ключи и APK удалены.
Исходники Android не менялись, набор из 26 тестов не перезапускался.
GitHub API списка secrets/runs возвращает 403: наличие/настройка реального секрета
и успешный CI не подтверждены. Нужна однократная настройка по README и успешный запуск.

Если старый приватный ключ случайного CI-runner утрачен, обновление старой установки
новым ключом невозможно. Переустановка удаляет локальные данные, настройки и разрешения;
до настройки постоянного ключа удаление приложения не рекомендуется. Новые APK нужно
проверять на обновление друг поверх друга с сохранением Room и DataStore.
